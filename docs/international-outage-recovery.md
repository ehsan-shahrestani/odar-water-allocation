# ادامه کار اودار هنگام قطع اینترنت بین‌الملل

هدف: وقتی Supabase Cloud، GitHub و رجیستری‌های خارجی در دسترس نیستند، اودار با آخرین بک‌آپ موجود در ایران دوباره قابل استفاده باشد.

این سند برنامه آماده‌سازی است؛ ایجاد آن به معنی آماده‌بودن سرور جایگزین نیست. هنوز استقرار کامل و آزمون بدون اینترنت بین‌الملل انجام نشده است.

## وضعیت فعلی

- آرشیو بک‌آپ شامل `roles.sql`، `schema.sql`، `data.sql` و `SHA256SUMS` است.
- بازیابی یک بک‌آپ واقعی روی دیتابیس آزمایشی در GitHub Actions موفق بوده است. این آزمون، راه‌اندازی کامل Auth، API و فانکشن‌های اپ را اثبات نمی‌کند.
- بک‌آپ شامل داده کاربران Auth و ساختار دیتابیس است، اما کد فانکشن‌ها، تنظیمات سرویس‌ها، کلیدهای محرمانه و نسخه ساخته‌شده اپ را ندارد.
- کلاینت فعلی آدرس Supabase Cloud را در تنظیمات build دارد. انتقال دیتابیس به‌تنهایی اپ نصب‌شده را به سرور جدید وصل نمی‌کند.
- زمان‌بندی فعلی بک‌آپ روی GitHub است و برای گرفتن بک‌آپ جدید به دسترسی Supabase Cloud نیاز دارد.
- `scripts/restore_public.py` برای ترمیم داده روی همان پروژه موجود است؛ ابزار راه‌اندازی بک‌اند جایگزین نیست.
- `scripts/verify_backup_restore.py` ابزار آزمون است و دیتابیس موقتش را در پایان حذف می‌کند؛ نباید آن را به جای بازیابی سرور عملیاتی اجرا کرد.

## آماده‌سازی قبل از قطع دسترسی

### ۱. سرور جایگزین داخل ایران

یک سرور لینوکسی مستقل با دسترسی SSH آماده شود. برای شروع، ۴ هسته، ۸ گیگابایت RAM و ۸۰ گیگابایت SSD پیشنهاد می‌شود؛ ظرفیت نهایی با آزمون بار و رشد داده تعیین می‌شود. دسترسی به فضای S3 بک‌آپ با داشتن سرور قابل اجرای Docker متفاوت است.

Supabase Self-hosted با نسخه ثابت و سازگار PostgreSQL، Auth و Edge Runtime نصب و اجرا شود. نسخه PostgreSQL هدف این پروژه ۱۷ است. نسخه‌های Auth و افزونه‌ها باید با بازیابی واقعی بررسی شوند؛ سازگاری صرفاً از روی شماره PostgreSQL نتیجه گرفته نشود.

### ۲. بسته کامل بازیابی در ایران

موارد زیر روی سرور و یک محل مستقل داخلی نگهداری شوند:

| مورد | دلیل |
| --- | --- |
| ایمیج تمام سرویس‌های Docker با نسخه و digest ثبت‌شده | نصب یا شروع مجدد بدون رجیستری خارجی |
| آرشیو ایمیج‌ها با `docker save` و دستور `docker load` | بازیابی روی سرور تازه یا پس از حذف cache |
| فایل‌های Compose، تنظیمات و اسکریپت راه‌اندازی | اجرای سرویس‌ها بدون دریافت کد از GitHub |
| هر هفت فانکشن و پوشه مشترک آن‌ها | ورود، پیامک و عملیات نماینده |
| وابستگی‌های بسته‌بندی‌شده یا cache پایدار و آزموده‌شده Deno | حذف نیاز به دانلود از `esm.sh`، `jsr` و npm هنگام اجرا |
| build آماده کلاینت و ادمین، شامل فایل‌های استاتیک | انتشار وب‌اپ بدون npm و build آنلاین |
| نسخه کامل سورس و فایل‌های lock | امکان نگهداری کد در نبود GitHub |
| چند بک‌آپ دیتابیس با checksum | انتخاب آخرین نسخه سالم |
| تنظیمات Auth، SMS Hook و دسترسی کاوه‌نگار | بازیابی رفتار ورود و پیامک |
| کلیدهای جدید محیط جایگزین و دسترسی فضای بک‌آپ | استقلال از تنظیمات Cloud |
| دستورالعمل بازیابی همراه ابزارهای نصب‌شده | اجرا بدون مراجعه به مستندات خارجی |

کلیدهای محرمانه در Git یا بسته عمومی اپ قرار نگیرند. یک نسخه امن از آن‌ها باید بدون نیاز به سرویس خارجی قابل دسترسی باشد. بک‌آپ دیتابیس کاربران به‌تنهایی جایگزین این تنظیمات نیست.

### ۳. مسیر دسترسی کاربران

دامنه اپ، API، DNS و گواهی HTTPS محیط داخلی پیشاپیش آماده و از شبکه کاربران داخل ایران آزموده شوند. اگر وب‌اپ خارج از ایران میزبانی می‌شود، نسخه آماده آن روی میزبان داخلی نیز قرار گیرد.

برای کلاینت فعلی، نسخه وب اضطراری با آدرس و کلید عمومی سرور داخلی ساخته و در ایران نگهداری شود. درباره نسخه Android یکی از این مسیرها باید قبل از حادثه اجرا شود:

- نسخه‌ای منتشر شود که تنظیمات عمومی بک‌اند را از آدرس تحت کنترل ما و قابل دسترسی داخلی دریافت کند؛ cache و تغییر محیط آن نیز آزمایش شود.
- APK متصل به محیط داخلی از قبل ساخته و از یک مسیر داخلی در اختیار کاربران قرار گیرد.

بدون این تغییر، APK قبلی همچنان Supabase Cloud را صدا می‌زند. کلیدهای جدید محیط جایگزین به ورود مجدد کاربران نیاز دارند؛ نشست قبلی Cloud نباید به عنوان ورود معتبر در محیط جدید پذیرفته شود.

### ۴. آزمون کامل پیش از حادثه

آخرین بک‌آپ روی محیط داخلی آزمایشی بازیابی شود. کدها و اثبات‌های موقت OTP/MFA و نشست‌های ورود قدیمی برای استفاده مجدد منتقل نشوند؛ کاربران در محیط جدید احراز هویت کنند.

با مسدود کردن دسترسی به سرویس‌های خارجی، شروع سرد همه سرویس‌ها و مسیرهای زیر بررسی شوند:

- دانلود وب‌اپ و دسترسی دامنه، DNS و HTTPS از شبکه داخلی.
- ورود نماینده، کشاورز و مدیر، همراه مرحله دوم ورود مدیر.
- مشاهده کشاورزان و سال‌های آبی، افزودن کشاورز، سهمیه و ثبت آبیاری.
- رد شدن دسترسی نماینده به چاه دیگری و سایر تست‌های دسترسی.
- ارسال پیامک واقعی فقط به شماره‌های مجاز تست `09152404098` یا `09905913852`، در صورت مجوز اجرای تست.
- گرفتن و بازیابی بک‌آپ بدون GitHub و Supabase Cloud.

cache موقت روی یک دستگاه کافی نیست. بسته ذخیره‌شده باید روی محیط تازه نیز قابل راه‌اندازی باشد. آزمون دیتابیس قبلی در GitHub جای این آزمون کامل داخلی را نمی‌گیرد.

## هنگام حادثه

۱. زمان آخرین بک‌آپ سالم و میزان داده ازدست‌رفته مشخص شود. داده‌های بعد از آن بک‌آپ، بدون منبع دیگری قابل بازیابی نیستند.

۲. عملیات نوشتن در محیط قبلی در حد دسترسی ممکن متوقف شود. اگر بخشی از کاربران هنوز به Cloud دسترسی دارند، باید از ثبت اطلاعات در دو محیط جلوگیری شود.

۳. بک‌آپ منتخب به مقصد تازه و جداگانه وارد شود؛ هرگز روی دیتابیس غیرخالی بدون بررسی بازیابی نشود. checksum، شناسه کاربران، تعداد رکوردها و عملکرد ورود کنترل شوند.

۴. سرویس‌های داخلی با تنظیمات آماده شروع شوند؛ فانکشن‌ها، کلیدها و SMS Hook نیز فعال شوند. شروع سرویس نباید دانلود خارجی بخواهد.

۵. پس از آزمون مسیرهای اصلی، اپ داخلی منتشر یا مسیر دسترسی به آن فعال شود. فقط محیط داخلی اجازه ثبت اطلاعات جدید داشته باشد.

۶. بک‌آپ محیط داخلی با زمان‌بندی محلی و ذخیره در مقصد مستقل داخلی فعال شود. گرفتن بک‌آپ جدید از Cloud هنگام قطع دسترسی امکان‌پذیر نیست.

## پس از بازگشت اینترنت

اتصال اپ‌ها خودکار به Cloud برنگردد. پس از اولین ثبت اطلاعات روی سرور داخلی، دو دیتابیس دیگر برابر نیستند. محیط اصلی انتخاب و انتقال تغییرات با بررسی شناسه‌ها و تعارض‌ها انجام شود. بازگرداندن بک‌آپ قدیمی روی محیط دارای داده جدید باعث حذف اطلاعات می‌شود.

## معیار آمادگی

تا زمانی که نسخه داخلی، از بسته ذخیره‌شده و آخرین بک‌آپ، با دسترسی خارجی مسدودشده راه‌اندازی نشده و ورود و ثبت آبیاری در آن موفق نبوده است، آمادگی اضطراری کامل نیست. زمان بازیابی واقعی از همین تمرین اندازه‌گیری و ثبت شود.

اگر ادامه کار با کمترین وقفه لازم است، انتقال محیط عملیاتی به ایران پیش از حادثه از اتکا به بازیابی پس از حادثه مطمئن‌تر است؛ بک‌آپ مستقل همچنان لازم خواهد بود.
