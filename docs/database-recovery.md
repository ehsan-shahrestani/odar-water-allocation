# بازیابی داده‌های اودار روی همان پروژهٔ Supabase

این راهنما برای پاک‌شدن اتفاقی **داده‌های برنامه** در پروژهٔ فعلی `mzibphdvuyemehboxown` است. اسکریپت `scripts/restore_public.py` فقط هفت جدول اصلی `public` را برمی‌گرداند. حساب‌های Auth، تریگرها، ساختار دیتابیس، Edge Functionها، Storage و کدهای یک‌بارمصرف ادمین را تغییر نمی‌دهد. آرشیو کامل دیتابیس را مستقیم به پروژهٔ غیرخالی وارد نکنید.

## پیش از حادثه

- آرشیوهای S3 را با چند نسخهٔ تاریخی نگه دارید. زمان بکاپ، آخرین زمانی است که امکان برگشت داده‌ها به آن وجود دارد.
- کلاینت‌های `psql` و `pg_dump` نسخهٔ ۱۷ یا جدیدتر را روی دستگاه بازیابی آماده کنید.
- روش را روی PostgreSQL محلی آزمایش کنید. آزمون روی پروژهٔ اصلی انجام نشود.
- Secretها و تنظیمات Edge Function و Auth خارج از بکاپ دیتابیس‌اند؛ برای خرابی این سرویس‌ها راهنمای جدا لازم است.

## بررسی آفلاین بکاپ

```bash
python3 scripts/restore_public.py /path/to/odar-supabase-backup.tar.gz
```

اسکریپت چهار فایل آرشیو و `SHA256SUMS` را بررسی می‌کند، بلوک‌های `COPY` را می‌خواند و تعداد رکوردهای بکاپ را نشان می‌دهد. دادهٔ شخصی را چاپ نمی‌کند. برای دیدن SQL بدون اتصال به Supabase:

```bash
python3 scripts/restore_public.py /path/to/odar-supabase-backup.tar.gz \
  --mode missing --render /tmp/odar-restore-missing.sql
```

فایل SQL شامل داده‌های حساس است و با دسترسی `0600` ذخیره می‌شود؛ آن را در Git یا ویرایشگرهای آنلاین قرار ندهید. این فایل برای PostgreSQL و اجرای `psql` روی دیتابیسی با ساختار همین پروژه ساخته شده است، نه برای کامپایلرهای عمومی SQL.

## انتخاب حالت

| حالت | رفتار | زمان مناسب |
| --- | --- | --- |
| `missing` | فقط شناسه‌های جاافتاده را اضافه می‌کند؛ مقدار رکوردهای موجود را عوض نمی‌کند | حذف چند رکورد یا چند جدول، وقتی داده‌های جدید باید حفظ شوند |
| `full` | داده‌های هفت جدول برنامه را کاملاً به زمان بکاپ برمی‌گرداند | خرابی گستردهٔ داده‌های برنامه؛ تغییرات جدیدتر از بکاپ از دست می‌روند |

هر دو حالت اگر حساب Auth متناظر با پروفایل‌های بکاپ وجود نداشته باشد متوقف می‌شوند. حالت `full` همچنین اگر فهرست کاربران Auth از زمان بکاپ تغییر کرده باشد متوقف می‌شود. برای حذف یا خرابی Auth از این اسکریپت استفاده نکنید.

## اجرای واقعی، فقط هنگام حادثه

1. عملیات نوشتن در اپ را متوقف کنید و آرشیوی را انتخاب کنید که پیش از حادثه ساخته شده است.
2. رشتهٔ اتصال دیتابیس **همین پروژه** را از Supabase Dashboard → Connect بردارید و فقط برای همین اجرای بازیابی در متغیر محیطی `ODAR_RESTORE_DB_URL` قرار دهید. آن را در `.env` همین سورس نگذارید: اسکریپت فایل `.env` را نمی‌خواند و فایل `.env` ریشهٔ پروژه نیز از Git مستثنا نشده است. در همان ترمینالی که فرمان بازیابی را اجرا می‌کنید، URL را با دستور زیر وارد کنید تا روی صفحه و در تاریخچهٔ فرمان‌ها نمایش داده نشود:

   ```bash
   read -r -s -p 'ODAR_RESTORE_DB_URL: ' ODAR_RESTORE_DB_URL
   printf '\n'
   export ODAR_RESTORE_DB_URL
   ```

   رمز دیتابیس را در رشتهٔ دریافتی از Dashboard جایگزین کنید. URL را در فایل مخزن یا خروجی فرمان‌ها ثبت نکنید.

3. یک پوشهٔ خصوصی و خارج از مخزن برای بکاپ اضطراری تعیین کنید. اسکریپت قبل از هر تغییری با `pg_dump` از ساختار و دادهٔ فعلی `public` بکاپ می‌گیرد.
4. حالت را مشخص و اجرا کنید:

```bash
python3 scripts/restore_public.py /path/to/odar-supabase-backup.tar.gz \
  --mode missing --apply \
  --confirm-project-ref mzibphdvuyemehboxown \
  --emergency-dir /absolute/private/emergency-backups
```

برای بازگشت کامل، `--mode full` را جایگزین کنید. اسکریپت داده را ابتدا در جدول‌های موقت می‌خواند، پروژه و کاربران Auth را بررسی می‌کند، سپس جدول‌های برنامه را قفل می‌کند. تریگرهای برنامه هنگام واردکردن داده موقتاً غیرفعال می‌شوند، ولی تریگرهای داخلیِ کلید خارجی فعال می‌مانند. واردکردن و کنترل نهایی در یک تراکنش انجام می‌شود؛ هر خطا باعث بازگشت کل عملیات می‌شود.

پس از اجرای اسکریپت، متغیر موقت را با `unset ODAR_RESTORE_DB_URL` از همان ترمینال پاک کنید.

بعد از موفقیت، تعداد رکوردهای اصلی، ورود ادمین و مسیرهای کشاورز/نماینده را بررسی و سپس نوشتن در اپ را دوباره فعال کنید. فایل بکاپ اضطراری را هم در S3 نگه دارید.

این اسکریپت برای همان پروژهٔ موجود و آسیب‌دیدن داده‌های `public` طراحی شده است. برای خرابی خودِ ساختار، Auth یا حذف کل پروژه، آرشیو دیتابیس و بازاستقرار سرویس‌ها مسیر جداگانه‌ای می‌خواهد.
